## 二、★ 为什么 code=37 无法预警封禁（本次最重要的认知）

这条决定了"安全线该盯什么"：

- code=37 是**无记忆的固定配额窗口**：320 次业务请求实测，各 50 次档位密度
  1/5.0–1/7.1，间距序列后段几乎全是 6，**不随当日累计量上升**
- 所以 **code=37 频率完全不能用来判断"离封禁还有多远"**
- 历史反例极硬：**08-03「156 条仅 1 次 code=37 就直接 code=32」**，
  另一次**「108 条 21 次 code=37 零封禁」** —— 相差 20 倍却结果相反
- 封禁走另一套机制（累计请求量 + 账号信任度），**且没有渐进信号，是直接封**

**推论**：唯一有意义的安全线是**单日累计请求量**（靠 `request_log` 账本执行），
不是 code=37 次数、也不是条内间隔。想控风险就压 `max_requests_per_day`。

由此清掉了三处"拿 code=37 当封禁预警"的遗留：
1. `boss.py` 的 `code37_limit` 从硬编码 35 改为读配置
2. `expand_list.py` 的 `recover_count > 12` → 读 `cfg.code37_limit`。
   这个 12 实测在 `Python开发工程师` 页10 触发并**掐断整轮**，
   导致 12 个新关键词和上海/深圳全都没跑到
3. 条内延迟不再被当作风险旋钮（见下）

## 三、三套档位

| | 保守 `hangzhou` | **稳定 `steady`（日常）** | 激进 `aggressive` |
|---|---|---|---|
| 条内延迟 | 4-6s | **3-5s** | 1.5-3s |
| 批大小 | 5 | **6** | 8 |

三城版 `config.cities3.yaml`（日线 1800）参数同稳定档，只是城市 ×3。

（每 5 条 vs 每 6 条）。配额窗口只认请求数不认时间，这点已独立验证三次。
所以"调慢求安心"是无效的，压总量才有效。

## 四、列表与详情**共享**同一 code=37 配额窗口

`scripts/probe_window_share.py` 交替混跑 20 次专项验证：

| 组别 | 样本 | code=37 间距 | 平均 |
|---|---|---|---|
| 纯详情 | 50 次 | `[6,6,8,5,12,5,6]` | 6.9 |
| 纯列表 | 37 次 | `[6,6,6,5,5,6]` | 5.7 |
| **混跑** | 20 次 | `[6,6,5]` | **6.7** |

判据：混跑时间距按**总请求数**算就落在 5-6，与单接口一致；若窗口独立，
混跑应稀释到约每 10 次总请求才触发。且混跑中两个接口都触发过
（seq 6/12 是 detail、seq 17 是 list）——独立窗口下详情仅发 2 次时不该触发。

**推翻**「风控几乎全在详情、列表便宜」这条长期认知。两类请求必须计入同一份预算
（日线按 `total` 卡是对的，账本按 `kind` 分类只为观测）。

## 五、★★ `pages_per_query` 是关键词的永久天花板（规模瓶颈的真正原因）

**机制**：`--dry-stop` 靠"连续 N 页零新增"提前收尾。第二轮跑同一个词时，
前几页必然全是已见岗位 → 立刻触发 dry-stop 跳过 → **页 N+1 以后永远到不了**。
于是"这个词已饱和"往往是被截断制造的**假象**。

**BOSS 搜索结果是「浅层各词共享、深层各词独有」**，三个词同一天实测同一模式：

| 页 | 后端开发工程师 | 向量数据库 | Python开发工程师 |
|---|---|---|---|
| 1-3 | 3, 2, **0** | 2, 1, 5 | **0, 0**, 1 |
| 4-6 | 9, 20, 28 | 14, 23, 24 | 1, 4, 7 |
| 7-10 | 29, 30, 30, **30** | 25, 21, 11, 21 | 9, 13, 13 |

- `向量数据库` 卡在 150 条（=5页×30）整整一周，不是没货
- `后端开发工程师` 页 7-10 每页 **29-30 条全新**，在天花板处被硬截断
- 单轮 328 条新增里这两个词贡献 328 条，**其余 13 词合计 1 条**

**`--dry-stop` 默认从 2 改到 5**：`后端开发工程师` 页3 恰好 0 新增，
dry-stop=2/3 会在最富的矿脉前一步掉头。

**新增 `keyword_progress` 表**记住每个 (城市, 关键词) 翻到第几页，下次续翻。
两种退出路径必须区分：
- **空 jobList** = 真到底 → 标 `exhausted`，以后跳过该词
- **dry-stop** = 只是这几页没新货 → **不标** exhausted，下次仍续翻

**评估关键词不能看浅层**：我一度按 `Python开发工程师` 页1-2 零新增判它
"被 python 覆盖、该砍"，结果页6→7、页7→9、页8→13 条 —— 浅层重叠、深层独立。
`analyze_keyword_yield.py` 的口径需按此复核。

## 六、多城市扩展

**BOSS 城市码**写进 `models.BOSS_CITY_CODES`（配置只写城市名即自动补码）。
来源 `GET /wapi/zpCommon/data/cityGroup.json`（免登录），用户核对过 URL 一致：
杭州 101210100 / 上海 101020100 / 深圳 101280600 / 北京 101010100 /
广州 101280100 / **全国 100010000**。**别猜**——码不是行政区划号。

**扩城市前必须做两件事，否则白花配额**：

1. **放开 `CITY_WHITELIST`**（`profile.py`）。两个消费者：`clean_local_db` 把
   外地岗降级成 sample、`export_pool_html.hard_drop` 直接剔除 —— 不改的话
   **新抓的沪深岗位抓回来就被丢掉**。已支持 `JOB_RADAR_CITIES=杭州,上海,深圳`，
   设 `*` = 全国不限；判定统一走 `P.city_allowed()`
2. **`expand_list.py` 原先只读 `cfg.cities[0]`** —— 配置写三城它也只抓第一个，
   **静默跑三倍时间抓同一批数据，日志毫无异常**。已改成遍历全部城市
   （城市在外层循环：同城连续翻更像真人、`lid` 会话按城市连贯），
   换城市时真导航过去并清空 `last_lid`

**关键词 13 → 27**。加词前用库内 `title like` / `job_description like` 命中数
当代理指标验证有量（列表和详情共享配额窗口，加空词等于白烧额度）。
特意**不加 `算法工程师`**（标题命中 141 但 JD 要 deepspeed/megatron/分布式训练，
与"应用层开发"错位）——这正是 RAG工程师/Prompt工程师跑题率 20-26% 的同源机制。

## 八、零请求数据修复

**又一批详情专属列被 `OVERWRITE_COLUMNS` 抹掉**：`job_status_desc`/
`position_name`/`recruitment_count`。这与 8-10 修的 `recruiter_active_status`
是同一个 bug，那次补了五个字段却**漏了这三个**。

抹除率按 `seen_count` 单调爬升是决定性证据：
`seen=2 → 0%(1/749)`、`seen=3-4 → 63%`、`seen=5-7 → 71%`、`seen=8+ → 85%(242/284)`。
已移进 `KEEP_IF_EMPTY_COLUMNS` + 三条回归测试防第三次。
（`recruiter_online` 留在 OVERWRITE 是对的：列表确实返回 `bossOnline`，
且"当前在线"是会来回变的实时状态。）

`backfill_from_raw.py` 零请求回填 **1413 行**：`detail_fetched_at` 235→1692
（终于能判断详情该不该重抓）、`job_status_desc` 1697、`district` 从 `address`
正则抽出 262。`recruitment_count` 回填 0 行 —— 印证平台压根不返回该字段。

**另修一个语义失真**：`upsert` 用 `payload["collected_at"]`（记录自带时间戳）
而非当下时间，backfill 从 DB 读回旧行时把旧时间戳带回来，导致 `last_seen_at`
被**往回写** —— 实测 144/235 行的 `last_seen_at` 早于 `detail_fetched_at`。
已改为取当下 UTC；存量数据仍是错的，故导出层算活跃度年龄用
`max(last_seen_at, detail_fetched_at)`。

## 九、显示层改造（子 agent 审查后实施）

**最严重的一条**：`risk_tags()` 把"工商未知"当风险，而工商数据靠事后富化，
于是**每轮新采集的岗位整批掉进风险页**——实测 133 条新增 active 全部只带
这一个标签，其中 48 条「刚刚活跃」，本该是 P0 头部。
已拆出 `real_risk_tags()`（只认低资本/新成立/非公司主体）用于分流。
同源第二半：`job_score` 在标签未提取时静默给技术分 0，让最新岗位也排最后 →
改为回退 JD 正文匹配。

**结果**：P0 73 → **139**，风险页 129 → **78**，超纲页 0 → **297**
（那页此前结构上永远为空：起薪>20K 的岗位要么被匿名公司规则剔除、
要么被"工商未知"抢走；而 490 条超纲岗全在 sample 里，页面却只读 active）。

**活跃度终于上了页面**（此前只体现在"你打开了哪个文件"这一层，`ACT_COLOR`
定义了从未被引用）。独立一列、可排序、按档位上色，超 7 天未刷新标
`⚠ N天前观测` —— 活跃度是抓详情那刻的快照，07-30 记录的"刚刚活跃"今天其实是
11 天前。

**两个静默失效的 bug**：点「公司」表头没反应（字符串走 `(x-y)` 得 NaN，
`Array.sort` 当 0 处理）；薪资排序忽略 `·N薪`（`15-25K·15薪` 中点 25.0 排在
`18-30K` 中点 24.0 下面，与页面自己的分桶口径矛盾）。

**新增投递追踪**：`chat_actions` 表建了但一直 0 行、从未写入。加了
`/apply`、`/note` 端点 —— "已投递"和"排除"是完全不同的语义，原先只有
`demote` 一个动作，投过的岗位会被移出池子，第二天打开页面不知道昨天投了哪些。

**安全**：`serve_pool.py` 有目录穿越，`GET /..%2F.env` 能读到含 API key 的
`.env`，而它还发着 `Access-Control-Allow-Origin: *`（任意网页的 JS 都能打
本机端口把文件读走）。已加 resolve 后路径校验 + 移除通配 CORS，实测穿越返回 403。
