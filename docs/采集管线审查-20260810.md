## ✅ 已修复（本次）

### P0 — `fetch` header 从未发出（token 一直是空的）

**位置**：`boss.py:178-192`、`expand_list.py:28-37`

**问题**：headers 被当作 `fetch(url, headers)` 的 init **顶层字段**传入，而不是嵌套在 `{headers: {...}}`。fetch API 只认白名单键（method/headers/body/credentials/...），其余键（Accept/token/X-Requested-With）静默丢弃。

```js
// 错误写法（项目当前）
const headers = { credentials:'include', 'Accept':..., 'token':... };
const r = await fetch(url, headers);  // ← Accept/token/X-Requested-With 全部被忽略

// 正确写法
const r = await fetch(url, { credentials:'include', headers: { 'Accept':..., 'token':... } });
```

**实测影响**：
- 所有请求从未带上 `token`/`X-Requested-With`/自定义 Accept
- `credentials:'include'` 恰好是合法顶层键 → cookie 一直生效 → 请求能成功，**掩盖了 bug**
- "detail 窗口 4-5 条"就是**不带 token 的裸配额**（记忆以为代码带了 token，实际没有）
- `_read_token()`/`_cached_token`/`FIXED_TOKEN` 整条链路是**死代码**，白花 evaluate
- `probe_detail_header.py` 的 A/B 对照（带 token vs 不带）实际是**同一组**（都没带），"固定 token 已失效"的记忆结论需修正

**修复**：改为 `fetch(url, {credentials:'include', headers})`，两个文件都改。

**⚠️ 改后必做**：带上 token 后配额行为会变（记忆说带 token 时能跑更多），旧的"4-5 条/窗口"与 `code37_limit=35` 阈值**全部失效**，须小样本重新标定再放量。

### P1 — `raw_json` 无条件覆盖抹掉 `raw.detail`（已丢 639 条，34%）

**位置**：`storage.py:212-221` `OVERWRITE_COLUMNS` 包含 `raw_json`

**问题**：
- `_collect_detail` 把详情 API 响应存进 `job.raw["detail"]`（`boss.py:548`），连同轮换后的新 securityId/lid
- 下一轮列表采集再见到这岗位时，upsert 用列表路径的 `job.raw`（只有列表字段）**无条件覆盖** `raw_json` → `detail` 块与新鲜 token 全部消失
- 实测：1891 条有 JD 的记录里 **639 条 `raw.detail` 已丢**（占 34%），且丢失组平均 seen_count 5.9 vs 保留组 4.29——被列表重复命中越多丢得越快

**这也是记忆里「492 条空活跃度 raw 无 detail，怀疑历史批次代码没写」的真相**：代码写了，是 upsert 覆盖掉的。

**修复**：`raw_json` 从 `OVERWRITE_COLUMNS` 移出，改成 merge——新 raw 覆盖列表字段但保留旧 `detail` 键。upsert 时读旧 `raw_json`，`{**old_raw, **new_raw}` 合并后写回。

### P1 — `backfill_resume.py` 口径不一致，空转 3+ 小时

**位置**：`backfill_resume.py:26-32` 的 `pending_count()`

**问题**：
- `pending_count()` SQL 无 `retention_status` 过滤
- 它调起的 `backfill_details.py` **默认加了** `AND retention_status='active'`
- 口径不一致 → pending_count 返回 231，backfill 实际选到 0 条 → 父进程判"可能全部跳过，重试" → sleep(600) → 循环 20 轮 = **3.3 小时白等**，每轮还白起一次 Chrome

**修复**：`pending_count()` 补上 `AND retention_status='active'`；"待补数没下降"时直接退出而非重试。

## ✅ 配额重标定（2026-08-10 晚，`scripts/calibrate_quota.py`）

修完 header bug 后所有旧配额数字都失效（等于裸配额），重标定 43 条 / 3 轮：

| 条内间隔 | 样本 | code=37 | 比例 |
|---|---|---|---|
| 10-14s | 12 | 0 | 0% |
| 7-10s | 12 | 3 | 25% |
| 5-7s | 11 | 2 | 18% |
| 3.5-5s | 8 | 1 | 12% |
| **合计** | **43** | **6** | **14%** |

**结论：code=37 是每约 5 条一次的 cookie 配额窗口，与条内间隔无关。**
三轮里 code=37 出现位置几乎重合（第 5-6、9-10、14-15 条），相邻间距
`[6,5,6,6,4,5]` 平均 5.3 条。最快档比中间档 code37 更少，是位置巧合而非提速有益。

推翻的旧假设：
- ❌「拉长间隔能减少 code=37」——不能，只是等更久。旧 `[8,12]` 是按时间制配的，纯浪费吞吐 → 改 `[4,6]`
- ❌「配额窗口要等 15-25 分钟恢复」——security-check 重算约 10s 即完整重置（三轮 6 次全部一次成功）→ `detail_cooldown` `[900,1500]` → `[90,150]`
- ✅ 真正的安全线是**单日累计请求量**（封禁按累计量+信任度算），已由 `request_log` 账本跨进程执行

**顺带修掉一个隐形浪费**：`SEARCH_BASE` 是 `/web/geek/job`（无 s），会 302 到 `/web/geek/jobs`。code=37 重算后回搜索页那次导航正好撞上 302 而超时，把重算后本该成功的详情重试白废一条配额（标定第二轮实测复现）。改成终态 URL 后第三轮 16/16 全成功。

**平台真不给活跃度**：5 条 active 重抓后 `bossInfo.activeTimeDesc` 仍为 `None`（`bossInfo` 有 11 个键就是没这个）。真实缺失，不是解析 bug——这正是 P1「平台未给」桶存在的理由，重抓也补不出来。

**本次标定顺带补数据**（不浪费请求）：活跃度空 17→5、`raw` 缺 detail 22→5、`detail_fetched_at` 4→43。全程零 code=32/36，8 份 dump 全是可恢复的 code=37。

## ✅ 第二轮大样本验证（2026-08-10 晚，账本记录 129+ 次业务请求）

### ② 列表与详情**共享同一 code=37 配额窗口**（`probe_window_share.py`）

| 组别 | 样本 | code=37 间距 | 平均 |
|---|---|---|---|
| 纯详情 | 50 次 | `[6,6,8,5,12,5,6]` | 6.9 |
| 纯列表 | 37 次 | `[6,6,6,5,5,6]` | 5.7 |
| **混跑** | 20 次 | `[6,6,5]` | **6.7** |

混跑时间距按**总请求数**算就落在 5-6，与单接口一致；若窗口独立，混跑应稀释到
约每 10 次总请求才触发。且混跑中两个接口都触发过（seq 6/12 detail、seq 17 list）——
独立窗口下详情仅发 2 次时不该触发。

**推翻**「风控几乎全在详情、列表零风控/便宜」这条长期认知。列表也是每约 5-6 次
一个 code=37，两类请求必须计入同一份预算（日线按 `total` 卡是对的）。

### ③ 配额窗口是**固定的、无记忆的**（`analyze_quota_curve.py`，320 次业务请求）

```
   1–50   7 次  1/7.1        151–200  9 次  1/5.6      301–320  4 次  1/5.0
  51–100  8 次  1/6.2        201–250  9 次  1/5.6
 101–150  7 次  1/7.1        251–300  8 次  1/6.2
```

密度全程 1/5.0–1/7.1，前半段 1/6.6、后半段 1/5.7 —— **不随当日累计量加密**。
间距序列后段几乎全是 6（`...6,6,6,5,6,6,5,6,6,6,6,6,6,5,6,6,5`），是**固定配额
窗口**的特征而非信用衰减计数器。

**实用换算（大样本校准）**：每约 6 条详情触发 1 次 code=37 → 抓 N 条 ≈ 1.17N 次请求。

**`code37_limit=35` 有了实测含义**：按每 6 条一次算，35 次 ≈ 约 210 条详情。
实测 `backfill_details --limit 200` 在 **162 条完成时**累计 35 次触发熔断主动停止
（另 6 条已下架不算）——**设计内行为，不是被平台风控**。

**但这只证明 code=37 不加密，封禁红线是另一回事，仍未实测**（也不建议实测）。

全程 **零 code=32/36、零节流文案**。当日总用量 372+/600。
